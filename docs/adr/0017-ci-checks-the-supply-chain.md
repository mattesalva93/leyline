# 0017: CI checks the supply chain

**Status:** accepted (2026-11-18)

## Decision

- **Actions are locked by the workflow lockfile**, `.github/workflows/actions.lock`, generated by `gh actions-lock` and checked by CI with `gh actions-lock --verify`. Workflows keep tag references. No SHA pinning in the workflow files.
- **The scanners are mise tools, not marketplace actions.** `zizmor`, `gitleaks` and `trivy` are pinned in `mise.toml` and run as plain commands in `ci.yml`, next to `pnpm audit`.
- **CI fails on a high or critical vulnerability with a fix.** An accepted one is listed with its reason: in `pnpm-workspace.yaml` (`audit.ignore`) for a dependency, in `.trivyignore.yaml` with an expiry date for an image.
- **Every workflow grants the token nothing**, and each job asks for what it needs.

## Why

- GitHub calls the lockfile "the strongest protection available", superseding SHA pinning: on top of the commit, it records the repository's ID and refuses a commit reachable only from a fork. It is generally available on the Free plan since 2026-10-28, and Dependabot updates it (`research/security-baseline.md`, section 6).
- An action that runs a scanner is one more third-party dependency in the job that guards the others; in March 2026 an attacker rewrote 76 of `trivy-action`'s 77 version tags (https://www.aquasec.com/blog/trivy-supply-chain-attack-what-you-need-to-know/). mise downloads each release from its project and checks it, the versions sit with node's and pnpm's, and the same commands run locally.
- A vulnerability with no fixed version leaves nothing to update, so it would only teach us to ignore red CI. An accepted image vulnerability expires because base images get rebuilt with the fix: the expiry makes CI ask again.

## Considered options

- **SHA pins with the version in a comment**: weaker than the lockfile, and noisier to read and review.
- **The scanners' own actions** (`zizmorcore/zizmor-action`, `gitleaks/gitleaks-action`, `aquasecurity/trivy-action`): rejected above.
- **`pnpm audit --prod`**: it would miss the dev tooling, where malicious packages land too.

## Consequences

- zizmor's lockfile support is experimental (from 1.32.0); a false `unpinned-uses` after a zizmor update means checking its release notes before suppressing anything.
- Changing any `uses:` needs `gh actions-lock` run again locally, or CI's verify step fails.
